# Repository Guidelines

## Project Structure & Modules

The backend is a Java 25 Spring Boot application. Production code lives in `src/main/java/ingatlanok/`, with business logic in `core/`, domain types in `model/`, persistence in `persistence/`, portal integrations in `portal/`, and HTTP endpoints in `web/` (each documented with a `package-info.java` module map). Backend tests and shared Object Mother builders (`TestFixtures.java`) are under `src/test/`. The React 19, TypeScript, and Vite frontend is in `frontend/src/`; unit tests and shared mock factories (`testFixtures.ts`) are in `frontend/src/test/` and browser tests in `frontend/e2e/`. `openapi/api-spec.yaml` is the API contract; regenerate frontend API types with `npm run generate-api` from `frontend/`. See `docs/architecture.md` for layer boundaries.

## Build, Test, and Development

- `./gradlew bootRun` (Windows: `.\gradlew.bat bootRun`) starts the backend on port 8080.
- `bash scripts/ai-verify.sh [--backend | --frontend | --all]` runs the compact, token-efficient verification runner (printing single-line PASS summaries or focused error excerpts).
- `./gradlew checkstyleMain checkstyleTest test jacocoTestReport jacocoTestCoverageVerification check bootJar` runs the full backend verification suite: javac fail-closed compiler flags (`-Werror`, `-Xlint`), exception-free ArchUnit architecture suite (`ArchitectureRulesTest.java`), Checkstyle Clean Code and whitespace/file-length rules, offline unit/integration tests, native Gradle `jacocoTestCoverageVerification` (>=80% line coverage), and packages the executable JAR.
- `cd frontend && npm ci && npm run dev` installs dependencies and starts Vite on port 5173.
- `cd frontend && npm run generate-api && npm run typecheck && npm run lint && npm run test && npm run build` runs the full frontend verification suite: OpenAPI client generation, strict TypeScript check (`noImplicitReturns`, `noImplicitOverride`, `forceConsistentCasingInFileNames`), ESLint zero-warning gate (`eslint . --max-warnings 0`) enforcing Clean Code and file-length metrics (`max-lines: 350`, `complexity: 15`, `max-depth: 4`, `max-params: 5`, `eqeqeq`, `@typescript-eslint/consistent-type-imports`, `@typescript-eslint/no-explicit-any: error`) and AST restriction against direct `window.open`, Vitest tests, and Vite production build.
- `cd frontend && npm run test:e2e` runs Playwright browser tests.
- `bash scripts/validate-skills.sh -v` (Windows: `& "C:\Program Files\Git\bin\bash.exe" scripts/validate-skills.sh -v`) executes deterministic offline validation of specialist skills, Markdown links, banned words/patterns, architectural guardrails, and frontend OpenAPI schema derivation (all 6 checks must pass).

Docker publication is handled by `.github/workflows/images.yml` (`Docker Build`), which runs on pushes to `develop`, and `.github/workflows/release.yml` (`Docker Release`), which is manually started from a branch (such as `main` or `develop`). Releases derive their version from the latest Git release tag and a patch/minor/major/custom input; GHCR publication must succeed before the Git tag and GitHub Release are created.

## Code Generation & Frontend Deduplication Conventions (Mandatory)

- **Lombok:** use `@Getter`/`@Builder`/`@NoArgsConstructor` (and `@Setter` only where post-construction mutation is needed) across models, presentation DTOs, and JPA entities. Prefer `@Builder` (with `@Builder.Default` or constructor-level `@Builder` for normalizing constructors, and `toBuilder = true` where copy-updates are needed) over setter chains across portal parsers, normalizers, core engines, and presentation services, and omit `@Setter` on read-only DTOs/value objects (`MarketStatsDto`, `MarketSegmentStatsDto`, `PriceDropItemDto`, `MarketStats`, `MarketSegmentStats`, `PriceDropItem`, `PortalStatusDto`, `DashboardResponseDto`, `PortalSource`, `PriceInfo`, `PropertyDetails`). Do not use `@Data`, `@EqualsAndHashCode`, `@ToString`, or `@SneakyThrows` (enforced by Checkstyle), and do not generate `equals`/`hashCode`/`toString` on JPA entities. Keep hand-written `equals`/`hashCode` where they encode business identity.
- **MapStruct:** use it for entity ↔ DTO/domain mappings (`JpaEntityMapper`, `PresentationMapper`) with `componentModel = "spring"` and `unmappedTargetPolicy = ReportingPolicy.ERROR`. Use `@AfterMapping` and `@MappingTarget` where post-mapping enrichment or merge semantics apply (`toItem`, `toProperty`, `updateEntityFromItem`), keeping only genuine stateful merge orchestration in Java. Add targeted unit tests for mapper null/fallback branches.
- **Records:** prefer `record` for immutable value carriers; classes with `@Builder` remain where Jackson/JPA or custom normalizing constructors apply.
- **Frontend OpenAPI Single Source of Truth:** derive all frontend DTO types (`types/property.ts`, `types/api.ts`, `types/portal.ts`) directly from `generated-api.ts` (`components['schemas']`) generated via `npm run generate-api`. Never duplicate OpenAPI schema interfaces by hand, and promptly remove unreferenced DTO types or unused API client functions (`api/propertyApi.ts`, `api/searchApi.ts`).
- **Frontend Domain & UI Deduplication:** centralize domain calculations, portal metadata (`normalizePortalKey`, `PORTAL_CHIPS`), quality-tier helpers (`clampQualityScore`, `getQualityConfig`), effective price/sqm helpers (`getEffectivePrice`, `getEffectiveSqmPrice`), and safe external link opening (`openExternalUrl` with `noopener,noreferrer`) in `frontend/src/utils/formatters.ts`, with market analytics math and aggregation helpers in `frontend/src/utils/marketAnalyticsMath.ts` and `frontend/src/utils/marketAnalyticsAggregation.ts`. Reuse shared UI primitives (`NumericStepper` for `AreaStepper`/`PriceStepper`, `useOutsideDismiss` for popovers/dropdowns, `SORT_OPTIONS` and `updateCriteria` in `useFilterStore`) and avoid redundant pass-through wrapper components.

## Style & Naming

Follow the existing Java package and class structure. Checkstyle 10.21.4 is strict: use 2-space indentation (`Indentation` with `basicOffset = 2`, no tabs), keep Java lines within 120 characters and production files within 450 lines (`FileLength` <= 450), enforce consistent token spacing (`WhitespaceAround`, `WhitespaceAfter`, `NoWhitespaceBefore`, `GenericWhitespace`, `EmptyLineSeparator`), group and sort imports, and avoid wildcard imports, `System.out`/`System.err`, `printStackTrace()`, and forbidden Lombok annotations (`@Data`, `@EqualsAndHashCode`, `@ToString`, `@SneakyThrows`). Clean Code metrics are enforced: `MethodLength` <= 80 (non-empty), `ParameterNumber` <= 6, `CyclomaticComplexity` <= 12, `BooleanExpressionComplexity` <= 4, `NestedIfDepth` <= 3, `NestedTryDepth` <= 2, and `DeclarationOrder`. Use descriptive PascalCase Java type names and camelCase members. Frontend components use `.tsx` with PascalCase names; hooks use `use`-prefixed camelCase. ESLint enforces Clean Code and modularity metrics (`max-lines: 350` excluding blanks/comments, `complexity: 15`, `max-depth: 4`, `max-params: 5`, `eqeqeq`, `@typescript-eslint/consistent-type-imports`, `@typescript-eslint/no-explicit-any: error`) and forbids direct `window.open`. Keep generated API types generated from the OpenAPI spec rather than editing them by hand.

## Testing

Add JUnit 5 tests under the matching `src/test/java` package (reusing `ingatlanok.testsupport.TestFixtures` for concise domain builders and `src/test/resources/logback-test.xml` for quiet `WARN`-level test logs) and Vitest tests in `frontend/src/test/` (reusing `frontend/src/test/testFixtures.ts` for OpenAPI-typed mock factories). ArchUnit JUnit 5 suite (`ArchitectureRulesTest.java`) asserts exception-free 4-layer unidirectional architecture (`core`, `persistence`, and `portal` never depend on `presentation`, `web`, or `config`), persistence layer abstraction, read-only DTO/model immutability, single-point SSRF isolation in `HttpFetcher`, and Java 25 virtual thread carrier-pinning prevention (no `synchronized` in service/portal/core/web). Add Playwright coverage in `frontend/e2e/` for user flows. Backend `check` excludes `live` tests; CI requires at least 80% Java line coverage enforced via native Gradle `jacocoTestCoverageVerification` bound to `./gradlew check`. Keep ordinary tests deterministic and offline.

## Commits & Pull Requests

Request GitHub Copilot as reviewer on every PR you create (`gh pr edit <id> --add-reviewer "@copilot"`). Agents must always set Copilot as a reviewer.

Use Conventional Commit subjects, such as `feat(search): add area filter`, `fix(portal): handle missing prices`, or `docs: clarify setup`. Use a descriptive branch prefix such as `feature/`, `fix/`, or `docs/`; target `develop` by default. PRs must use concise, high-signal Hungarian descriptions adhering strictly to the template's 5 core sections (`🎯 Miért készült?`, `🛠️ Mit módosít / Mit javít?`, `📋 Acceptance Criteria Traceability`, `🧪 Tesztelés és Ellenőrzés`, and `🛡️ Thematic Agent Approval Gate` with standard decision tokens `[NO_FINDING]`, `[NOT_APPLICABLE]`, rejecting `[NOT_VERIFIED]`, `[FINDING]`, and legacy `[OK]`, accompanied by 1-sentence rationales per the Review Risk Matrix in `docs/pr-compliance.md`), link related issues with closing keywords (`Closes #<id>`), and strictly enforce clean UTF-8 encoding (`gh pr create --body-file ...`) without BOM to prevent mojibake. All required CI checks must pass before merge.

## Issue Creation & Tracking Guidelines

When creating GitHub issues (manually or via `gh issue create`), always use the formal templates located in `.github/ISSUE_TEMPLATE/` as the single source of truth:
- **Bugs:** Follow `.github/ISSUE_TEMPLATE/bug_report.yml` (`fix: <description>` title, `bug` label, problem description, expected vs actual behavior, reproduction steps, affected component, environment, logs).
- **Features / Enhancements:** Follow `.github/ISSUE_TEMPLATE/feature_request.yml` (`feat: <description>` title, `enhancement` label, user need / problem, proposed solution, affected specialist component / agent, alternatives).
- For automated/CLI creation, generate markdown adhering directly to the YAML schema's required sections to ensure uniform structure and high signal across all issues.

## Efficient Issue Implementation & CI Validation

- Before a broad change, turn every issue acceptance criterion into a checklist and map it to the affected code, API contract, tests, and CI/security gates. Inspect the relevant workflow files and existing validation scripts before implementation so requirements such as Checkstyle, JaCoCo, OpenAPI generation, and CodeQL are known up front.
- Implement the complete change in coherent, reviewable slices. Keep related production changes, compatibility updates, and their tests together; avoid publishing one-assertion test commits, syntax/style fixups, or successive trial-and-error security patches.
- Validate locally before the first push using `bash scripts/ai-verify.sh --all` and the full verification suites (`./gradlew checkstyleMain checkstyleTest test jacocoTestReport jacocoTestCoverageVerification check bootJar`, `npm run generate-api && npm run typecheck && npm run lint && npm run test && npm run build` in `frontend/`, and `bash scripts/validate-skills.sh -v`). Resolve all findings from that pass together before pushing.
- For logic changes, add happy-path and boundary/error-path tests in the same implementation slice. Keep Java line coverage safely above the repository's 80% CI minimum (target at least 82%) so later small edits do not make the PR fragile.
- For security-sensitive networking, identify the tainted input and the final network sink before coding; use the shared validated `HttpFetcher` path where applicable. Review the repository's CodeQL rules and make validation explicit at the sink when static analysis cannot recognize an indirect sanitizer. Do not rely on repeated remote CodeQL failures to discover the required pattern.
- After pushing, verify required checks against the PR's current head commit and inspect the failed job's steps/logs before changing code. Batch all fixes revealed by a run into one local correction, rerun the relevant local checks, then push once. Do not push a new commit merely to retrigger checks that already passed.
- Prefer a small number of Conventional Commits, each representing a complete logical increment. Keep temporary checkpoints local; publish a commit only when its state is coherent and validated. A wide refactor can still use multiple commits when each is independently meaningful, but do not split mechanical fixups into separate remote commits.

## Configuration & Security

Use `.env.example` as the configuration reference; never commit secrets or real credentials. Development uses embedded H2, while Docker Compose configures PostgreSQL. Review `SECURITY.md` before reporting vulnerabilities.
